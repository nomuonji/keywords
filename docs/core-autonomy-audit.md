# 記事制作を中心にした再設計監査

追補：ユーザーの追加方針によりUIは任意の進捗確認用とし、ヘッドレス実行を主とする。生成効率・中断復旧・最短成果物の詳細は [headless-generation-improvement.md](headless-generation-improvement.md) を参照。候補選択と停止session除外は追補時に修正・隔離DB検証済み。それ以外の表は改善仕様であり完了済みではない。

2026-09-09。Keywordsの実装、稼働API、直近の実行ログ、Blog連携文書とbridgeコードを確認。全サイトの公開疎通・記事本文品質・ブラウザの実画面は今回未検証。以下は確認済みの欠陥と設計上の改善案であり、全項目の修正完了報告ではない。

## 到達目標

ユーザーは対象サイト、編集方針、費用・本数上限、公開モードを初回に指定する。以後はエージェントが材料収集、企画、執筆、検証、修正まで進める。通常の操作は完成記事を見ることと停止すること。公開は記事生成とは別の許可設定で扱う。

完了は「プロセス終了」でも「企画承認」でもなく、本文ファイル、原典、検証結果、差分への参照が揃った状態とする。公開完了と検索成果はさらに別の状態。

## 消す・隠す・残す

削除対象：重複進捗パネル、装飾的なフェーズレール、二重scheduler、同一版の再採点、失敗時の無条件再登録、自己採点だけの公開判定、成果未確認の自動完了。

通常画面から外す対象：keyword全件編集、cluster操作、手動handoffダウンロード、work session操作、policy管理、runログ。必要な機能は詳細・保守画面とCLI/MCPに残す。永続データを消す意味ではない。

残す対象：SQL正本と共有commands、sourcesと実測履歴、本文と差分、Blogの既存build/内容検証、冪等性、予算、lease、監査、バックアップ、例外時の判断、緊急停止。

## 主画面

入口は「記事」。上部に運転状態と共通障害を一か所だけ表示。その下に完成記事と制作中の記事を並べる。各記事にはサイト、タイトル、状態、最終進展、本文/差分を表示。ユーザーの判断が必要なものだけ専用欄に出す。サイト一覧と接続設定は別画面。初期画面から手動SEO工程を順番に操作させない。

## 実装の順番と受入条件

1. 実行基盤：正しい候補選択、共通障害での待機、再開、成果確認、scheduler一本化。1サイトの問題で他サイトを止めず、利用上限中は追加の失敗を作らない。
2. 1記事の縦通し：接続済みサイトで資料→企画→本文→レビュー→修正→ローカル検証まで。本文ファイル・根拠・差分を画面から開けるまで完了にしない。
3. 主画面を記事中心に置換。重複画面を撤去し、通常制作での人間操作をゼロにする。
4. 複数サイトへ展開。上限、公平性、費用、復旧を確認して対象を増やす。
5. 公開モードが許可されたサイトのみ既存公開経路へ接続。下書き生成の成功を公開成功やSEO成功と混同しない。

主要指標：完成記事数、記事ごとの実行費用・所要時間、通常制作への人間介入回数、修正回数、進展のない再試行回数。tick数やOperation数は成果指標から外す。

## 今回の変更範囲

監査と処置方針を作成し、前回導入した存在しないSQL列参照を撤去した。自動実行の再開、本文生成、画面の全面置換、データ削除はまだ実施していない。過去の「型チェック通過」は実行時のキュー動作や記事生成の保証になっていなかった。
