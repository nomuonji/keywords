作成日: 2026-09-08

## 1. 目指す状態

ユーザーが「このサイトで次に何を狙うか」を決め、その根拠を確認し、記事企画を承認できるワークスペースにする。初回利用ではサイトやテーマの登録から新規候補の取得まで進められ、翌日には前回の結果と未完了作業から再開できることを目標とする。

共通SQLとコマンド層、証拠ソース、作業セッション、人間レビューという既存の土台は維持する。記事本文生成・CMS連携・公開は引き続き対象外とする。

最初の実用化の到達点は、次の一連の操作である。

1. サイトまたはテーマ、対象言語・地域を設定する。
2. 「新しいキーワードを探す」から探索条件と上限を指定する。
3. 取得した候補の需要・検索意図・既存ページとの重複・証拠を確認する。
4. 候補を採用・保留・除外し、クラスタと記事企画へ進める。
5. 人間が根拠を見て企画を承認し、企画書を持ち出せる。
6. 再訪時に結果、残作業、次の推奨が更新されている。

### 前回の探索結果を扱う際の注意

前回は本番サイトではなく、ドメイン未設定のテストプロジェクト「Planning Smoke」に6語を登録した。元の英語シードから日本語のSEO関連語へ対象を広げたが、対象読者・言語の適合性を決めていない。この6語は探索デモの候補であり、実サイトへの推奨語ではない。

また、次の点は今後の実装とデータ再確認で是正する必要がある。

- Adsプロキシの値は取得地域・言語・日時付きの推定値として扱う。広告competitionの低さから「SEOで競合が弱い」とは判断しない。
- Googleサジェスト0件は需要なしを証明しない。Bingの関連候補も、元の検索語の需要や検索回数を証明しない。
- 保存したソースには、個別には確認していない語への「Bing候補あり」や、精査していない競合についての評価が含まれる。実測、関連語からの推定、未確認を分けて再確認する。
- 上位10件の比較、AIO、allintitle、クラスタ間のURL重複は未検証。詳細な競合判定を完了扱いにしない。
- 外部調査が共有コマンド経由ではなかったため、セッションの7/8 actionsは全調査量を表していない。
- SQLiteとdataディレクトリはGit管理外。前回のpushにキーワードデータは含まれていない。

本提案ではこれらの既存データを変更しない。再評価を実装後のデモ移行条件に含める。

## 4. 具体的な修正案

### A01 初期設定と接続診断

プロジェクトに対象サイト、テーマ、対象読者、言語、国・地域、除外テーマを設定する。「サイト運用中」と「テーマから新規企画」を選べるようにし、GSCやサイトマップをまだ持たない利用でも探索を開始できるようにする。

接続状態は未設定・確認中・利用可能・期限切れ・利用制限・失敗を区別する。設定画面には接続テスト、最終成功時刻、復旧方法を示し、認証情報の値は表示・保存しない。現在の環境変数読み込み手順も起動方法ごとに検証する。

サンプルは「デモ」と明示し、実サイトと選び間違えない導線を用意する。テスト用検索数を実測として表示しない。

受け入れ条件: 新規サイトなし・GSCなしでもテーマを指定して探索できる。Adsが未設定なら使えない理由と利用可能な探索手段が分かる。プロジェクトの対象言語をエージェントが暗黙に変更しない。

### A02 フォームと更新処理

現在のcreateProject/addKeyword/addTask/fetchEvidenceはawait後にe.currentTarget.reset()を呼ぶ。非同期処理後のイベント参照に依存しないようフォーム参照を先に保持し、成功後のリセットと再取得を保証する。失敗時は入力を保持して同じフォーム内に理由を出す。実装時にブラウザで再現確認する。

Tick・同期・メトリクス取得・レビュー・MCP経由の変更で、関連する件数、一覧、詳細、作業状態を更新する。プロジェクトIDを含む取得キーとリクエスト取消または世代管理を導入し、切替前の応答が新しい画面へ混ざらないようにする。

全APIリクエストを直列化する現在の対処は、長い調査が別の画面取得を塞ぐ。タイムアウト、取消、同一取得の重複抑制を設け、読み取りは制限付き並列化を検討する。SQLite依存問題の修正と、UIの通信制御を別の検証項目にする。

受け入れ条件: 登録成功後の再読込が不要。Tick後にタスク数と一覧が一致する。遅い通信中のプロジェクト切替で前のデータが表示されない。連打や再試行で同じ登録が重複しない。

### A03 新規キーワード探索

ホームに「新しいキーワードを探す」を設ける。入力はシード語または対象URL、言語・地域、探索目的、除外語、調査上限。プロジェクト設定を初期値にし、探索時の上書きは明示的に残す。

実行前に利用プロバイダーと見積可能な呼出数・費用を示す。最初は既存Adsコマンドを画面から使えるようにし、サジェスト等の補完はpackages/researchの読み取りアダプターとして追加する。ローカルの個人スキルや外部プロキシがない環境でも、対応機能と設定不足を判別できる設計にする。

探索では候補生成、重複確認、必要な需要取得、優先候補のSERP確認を予算に応じて行う。一律に全候補へ全APIを叩く固定パイプラインは避ける。途中結果と次に何を調べるかをセッションに残す。

結果には新規・既存・除外・評価待ちの件数を示す。候補は共有keywordsの候補状態として扱い、保存と採用を区別する。評価前の語が即「推奨」になることを避け、状態追加はDB移行を伴う提案とする。ユーザーは採用・保留・除外・追加調査を選べる。

受け入れ条件: 1つのシードから候補を取得し、原語・取得条件・証拠を辿れる。0件、全件既存、認証失敗、途中失敗で異なる結果を示す。同条件の再実行はデータ重複を起こさない。

### A04 指標と証拠

Adsのcompetitionは「広告競合度」と表記する。SEOで狙うかどうかは検索意図、上位ページ内容、既存サイトとの適合性、独自の情報を提供できるかを別々に記録する。広告competitionをSEO難度として利用するlowCompetitionDemandの名称・説明・優先計算は見直す。

数値ごとにプロバイダー、取得日時、対象地域・言語、対象期間、元のキーワードを保持する。表記統合した結果と元語の対応を残す。未取得・取得不能・0を区別し、nullや空文字列の数値変換も検証する。近似語の検索数を単純加算して市場規模を作らない。

sourceとkeywordの明示的な参照関係、および観測履歴をDB層で設計する。source文字列だけに依存しない。SERP証拠はquery、取得日時、国・言語、URL・順位・タイトル等を保持し、所見には根拠URLと確認済み範囲を付ける。全件精査していない場合は「概観のみ」と示す。

Sources詳細から取得条件、保存内容、対象語、所見、関連企画を辿れるようにする。以前の所見を後で訂正したことも記録できるようにし、誤った評価の上書きだけで履歴を失わない。

受け入れ条件: 任意の検索数について出典と条件を説明できる。広告競合0・SERP未調査の語を「SEO低競合」と表示しない。サジェスト非出現だけで候補を除外しない。

### A05 セッション・予算・監査の共通保証

MCP内のactiveWorkSessionは補助情報に限定する。セッションの所属プロジェクト、状態、残予算をcommands層でSQLから検証し、API・CLI・MCP・スケジューラーに共通適用する。

並行実行時の予算予約、成功・失敗時の精算、外部調査の呼出上限を定義する。1つのコマンドで何千件も調査できる抜け道を避けるため、コマンド数と外部リクエスト数・取得件数を分けて管理する。画面には理解しやすい上限を出す。

関連レコード変更と成功監査は可能な範囲で同じトランザクションにする。外部取得中にDBトランザクションを保持せず、取得前の予約と取得後の一括保存に分ける。失敗監査はロールバック後にも残す。

HTTPの自己申告actorヘッダーだけでは人間であることを保証できない。ローカル利用範囲・許可Originを明確にし、人間レビュー操作の権限と入力検証を設計する。これは現在の人間承認ルールを全入口で守るための実装項目であり、新しい承認段階を増やす提案ではない。

受け入れ条件: awaiting_review・blocked・予算超過を別入口から迂回できない。並行コマンドで予算を超えない。別プロジェクトのIDを混ぜると変更前に拒否される。失敗後も状態と監査が整合する。

### A06 キーワード一覧と詳細

全件一覧に検索、並べ替え、ページ送り、件数、複数選択を設ける。絞込は候補状態、クラスタ、取得元、需要の有無、未調査、既存ページへの割当を基本とする。1000語以上でも全件をブラウザへ一括転送しない設計にする。

詳細には検索数、広告競合度、SERP所見、GSC履歴、所属クラスタ、対象ページ、関連証拠、採用・保留・除外理由をまとめる。数値がない語も確認できる。CSV入出力はプレビューで文字コード・列・重複・取込条件を確認し、取り込みをコマンドとして監査する。

受け入れ条件: 13件目以降を探せる。クラスタ所属語を開ける。選択した語だけを一括で移動・保留できる。取込の再試行が二重登録にならない。

### A07 クラスタと記事企画

クラスタをクリックして所属語と既存ページを開けるようにする。名前変更、語の移動、統合、統合理由を共有コマンドで扱う。SERP重複は参考材料として提示し、固定閾値だけで同一意図を確定しない。

企画は対象読者、解決する問い、主・副キーワード、独自に提供する情報、参照ソース、既存ページとの差、未確認事項を含む。新規作成と既存ページ改善を選べるようにし、カニバリゼーションの競合ページを相互に開けるようにする。

レビュー画面で証拠と企画を同時に確認し、承認・修正依頼・却下へ進める。承認は公開を意味しないことを表示する。Markdown/CSVとして企画を持ち出す際にも証拠参照とステータスを含める。

受け入れ条件: 1件の探索候補から根拠付き企画を作り、人間が承認できる。類似する既存ページがあれば新規企画前に確認できる。

### A08 タスクと実行者

「Tick」は「次の作業を選ぶ」など結果が分かる名称に変更し、作成したタスクへリンクする。タスク選定と実行開始は別の状態として表示する。

初期実装では外部MCPエージェントに作業を引き渡す方式を推奨する。タスク詳細に目的、完了条件、予算、開始方法、接続状態、実行者、最終更新時刻を示す。実行者が未接続なら待機理由を表示する。アプリ内実行器を追加する場合は、モデル接続、費用、停止、再起動時の復旧を別設計として扱う。

既存タスクが永久に新規探索を遮らないよう、実行可能性・関連セッション・接続不足・放置状態を評価する。ドメインなしでサイト同期だけを推奨し続けない。レビュー待ちセッションの停止は守りながら、無関係な作業をどう扱うかは明示的なルールにする。

受け入れ条件: todoからdoing、reviewまたはdoneまで進められる。作業を請け負うエージェントがいない場合に「実行中」と表示しない。複数実行者が同じタスクを重複実行しない。

### A09 GSCとサイト同期

比較は同じプロパティ、検索種別、同じ長さの期間を基本にし、比較対象を選べるようにする。未完了期間、重複期間、片側だけに存在する語、取得上限を明示する。現在のquery/URL単独による組み合わせと、上限5000行を総件数のように表示する点を見直す。

期間履歴の置換は一括コミットし、途中失敗で履歴が半分だけ残らないようにする。GSCページ結果のページネーション・取得完了条件も確認する。

サイト同期は新規、更新、未観測、エラーを分けて結果表示する。URL正規化とslug衝突を検証し、同名slugという理由だけで別URLを結び付けない。既存ページの削除を未観測だけで断定しない。

受け入れ条件: 7日対28日の単純なクリック減を順位低下タスクとして扱わない。同一期間の再取得が冪等で、失敗時には既存の正常な履歴を保持する。

### A10 情報構成と操作の言葉

ホームは「次の作業」「実行中」「確認待ち」「最近の成果」に絞る。詳細は次の画面へ分ける。

| 画面 | 主な用途 |
|---|---|
| ホーム | 今日の推奨、実行状態、結果を確認 |
| キーワード探索 | 条件指定と候補取得 |
| キーワード | 全件確認、選別、証拠参照 |
| コンテンツ計画 | クラスタ、既存ページ、企画 |
| 検索実績 | GSC比較とサイト同期 |
| 作業・レビュー | タスク、セッション、人間判断 |
| 設定 | 対象、接続、運用ルール、データ管理 |

日本語を初期表示にする。Work sessionsは「作業履歴」、Sourcesは「調査の根拠」など、利用目的で命名する。内部コマンド名は診断詳細に残す。

空欄を未取得・取得中・0件・失敗に分け、読み込み中に「No action」「異常なし」と断定しない。承認ダイアログの取消は変更なしとする。現在のwindow.prompt取消後も送信し得る経路を確認する。

入力には表示ラベル、フォーカス表示、エラーとの関連付けを設ける。キーボードで探索・選別・レビューを完結できるようにする。狭い画面では一覧の必須列を優先し詳細へ展開する。

予算消費率は「上限の消費」と表記し、進捗は完了条件と成果で示す。活動ログは変更と失敗を初期表示し、読み取り記録は絞込で参照する。

受け入れ条件: 初見ユーザーが説明なしに探索入口、結果、次の操作を発見できる。読込中と0件を区別でき、取消でレビューが送信されない。

### A11 起動とデータ保全

利用Node、依存解決、DBパス、API接続、環境変数読込を確認する診断コマンドを用意する。API・CLI・MCPの作業ディレクトリによって別SQLiteを開かないよう、共通の絶対パス解決方針を定める。

今回の旧SQLite依存リンク問題を踏まえ、使用するパッケージマネージャーとロックファイルを統一し、クリーンインストールで再現検証する。互換性のための全通信直列化を恒久策にしない。

SQLiteの整合したバックアップ、復元、移行前バックアップを提供する。Gitのコード保存と、ユーザーの調査データ保存を設定画面・READMEで区別する。実行中SQLiteを単純コピーする方法を復元保証としない。

受け入れ条件: 別プロセスのCLIと画面が同じプロジェクトを見る。停止・起動後も状態が一致する。バックアップから別の検証DBへ復元して件数と参照整合性を確認できる。

### A12 継続運用

探索の頻度、1回の上限、対象テーマ、再調査までの間隔をプロジェクト単位で設定する。既存候補を何度も取得しないよう探索条件と日時を保持し、採用・除外理由を次の候補評価に渡す。恒久ポリシーの有効化は既存の人間レビューを維持する。

探索件数だけでなく、採用率、企画化率、保留理由、費用、後日のGSC変化を振り返る。単純な前後比較だけで探索の効果を断定せず、対象期間と他の変更を併記する。成果が出る前は探索・企画の完了率を運用品質の指標とする。

## 5. 実装境界

- `packages/db`: 設定、候補状態、証拠参照、観測履歴、実行予約などの共通スキーマと移行。
- `packages/research`: Ads・SERP・サジェスト等の外部読み取り、応答の正規化。workspaceへの書き込みはしない。
- `packages/commands`: 保存、選別、採用、タスク状態、予算、停止条件、監査、整合性。
- API・CLI・MCP・Web: 同じコマンドの入出力。独自のSQL書き込みやエージェント専用状態を追加しない。
- Operator: 理由付き優先順位とタスク作成。SEO作業の実行器を内包させない。
- 認証情報: 環境変数または環境側の秘密管理で扱い、source・runsを含むSQLに保存しない。外部エラー本文の保存前にも秘密情報を除去する。

API仕様と型の共有、入力検証、状態遷移エラー、冪等キーを共通化する。大量の改修を一括で行わず、上記の業務単位で既存入口との互換性を検証する。

## 6. 推奨する実装順

### 第1段階: 操作結果と判断材料を信頼できる状態にする

A02のフォーム・画面更新、A04の広告競合の誤解防止、A05の共有制約、A11のDBパスと再現可能な起動を実施する。古い探索デモの評価を未検証として見直す。

出口: 更新遅延や二重登録で迷わず、どの入口でも同じ制約とデータを使う。

### 第2段階: 新規探索を画面から完結させる

A01とA03を実装し、A06の基本一覧、A04の証拠詳細、A10の最小ナビゲーションを揃える。まず1つの設定済みプロバイダーで探索から候補確認まで通す。

出口: ユーザーが自分のテーマで探索を1回行い、結果の根拠と未検証箇所を確認できる。

### 第3段階: 候補から企画の承認までつなぐ

A07、A08の外部MCP引き渡し、レビューUIと再開処理を実装する。

出口: 探索→選別→クラスタ→根拠付き企画→人間レビューを1件完了できる。

### 第4段階: 継続運用を成立させる

A09、A11のバックアップ・復元、A12を実施する。実行器の内蔵は、この段階までの利用結果と運用コストを見て判断する。

出口: 再起動・翌日の再開・同期失敗からの復旧を含めて、日常業務を継続できる。

期間見積は未確定。実行器の内蔵有無、利用する調査プロバイダー、既存データ移行量によって差が大きいため、各段階の出口条件で分割する。

## 7. 実用化の検証シナリオ

| シナリオ | 合格条件 |
|---|---|
| 初回・サイトなし | テーマと言語を設定し、利用可能な手段で探索開始できる |
| サイト運用中 | 同期済みページと新規候補を比較し、新規と改善を選べる |
| 新規候補取得 | 候補ごとの数値と証拠条件が一致し、採否を記録できる |
| 件数増加 | 1000語規模で検索・絞込・全件到達ができる |
| 外部API失敗 | 入力と成功済み結果を保持し、再試行で重複しない |
| 人間レビュー待ち | 別アダプターや再起動で停止状態を迂回しない |
| 同時実行 | 同じタスクの重複claim、予算超過、二重登録を防ぐ |
| プロジェクト切替 | 遅延応答が別プロジェクトの表示や操作へ混ざらない |
| GSC期間比較 | 比較条件不一致と取得上限を明示し、誤った減少を推奨しない |
| 再開と復元 | DB復元後に候補、証拠、セッション、レビューを辿れる |

型チェックと既存smokeに加え、上記の主要フローを実ブラウザで確認する。外部APIは通常テストで固定応答を使い、設定済み環境で少量の実接続を別途確認する。テスト用データと実測データを混ぜない。

使いやすさの目標値は、初見ユーザーが5分以内に探索を開始し、再訪時に1分以内に前回の成果と次の作業を把握できること。これは現状の達成値ではなく、実装後の利用テストで検証する仮目標である。

## 8. 実装前に置く前提

- 第一対象は日本語UIを使うローカル単独利用者。多人数向けクラウド化は別設計。
- 外部MCPエージェントを初期の実行者とする。常駐実行器・モデル費用は今回確定しない。
- 対象サイト・言語・地域はプロジェクト設定で明示する。テスト用SEO語を既定の本番テーマにしない。
- 需要値だけで推奨を確定しない。未調査候補を保持して、追加調査の対象として扱う。
- 最初の実装対象は第1段階と第2段階。装飾中心の全面リデザインより、探索の業務完了を優先する。
