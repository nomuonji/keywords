# SEO事例研究：横断コーパス優先（v1.22）

## 運用方針

**新規実例の収集 ＞ 分野横断の比較 ＞ 仮説の検証 ＞ 個別サイトの再観測。**

ユーザー決定（2026-10-18）：毎回同じドメインの順位履歴を更新するための時間をかけない。まず広いテーマで大量の実例を集め、サイトテーマの発見と既存サイトのSEO記事改善双方の研究素材にする。新しいクロールやGSCの効果測定が要るのは、具体的な仮説が成立してから。新設サイトの発掘に限定しすぎず、客観的に「若いドメイン登録／登録日不明」を区別し保存する。古いドメインも比較対象として検証可能だが、現段階のコーパスには自動採用しない。

## どこに保存されるか

Keywords Operator Firestore の **seoCaseSites** コレクションがドメイン単位で1レコード（ハッシュID）。既存のSERPキャッシュは取得元であり、事例DBの代用ではない。SEO実務家やSEOニュースを収集する既存の **seoSourceAccounts / seoSourceScans** とも別で、知見DBの重複ではない。

- 初回発見日、登録日／登録不明と照会根拠、検索結果から見つかったURL・タイトル・検索語・順位・プロバイダー・取得日時、調査テーマ、実ページの最大1000字断片を保存。
- 既存ドメインは**通常スキップ**。初回発見の証拠を保持し、順位履歴を毎回更新しない。差分比較が必要なら従来の \`young_domain_serp_research\` または登録サイトのGSCを別途使う。
- 生ページ本文や転載記事の大量保管はしない。URLと短い証拠断片を残し、検証時には原本を再読込する。
- サイトの「勝因」や「成長」は推測しない。**registrationStatus** は \`recent_registration\` と \`unknown\` を分け、後者を新規サイト認定しない。獲得トラフィック・売上・バックリンク・実開設日はいずれも未確認。
- テーマ \`topic\` は **収集時の関心分類**。事実としてのサイト業種やユーザーのGOOD判定ではない。サイトアイデアとして採用する時は、既存のKeywords Idea Memoryの重複審査・最終評価を別途行う。

## ツール（Keywords MCP）

\`seo_case_collect\`: \`{ "topic": "piano learning", "queries": ["flowkey vs simply piano", "best piano app for adults"], "country": "us", "language": "en", "includeUnknownAge": true }\`

1回で最大5検索語、RDAP最大8件、本文最大4件。**SERPは既存キャッシュ/上限管理を使う。** 初回の新ドメインだけcreate-onlyで一括保存し、実際の新規件数、既登録件数、未確認や取得失敗を返す。0件なら0件と記録し、勝手に条件を緩めて架空の成功例を登録しない。正常な0件は検索・資料選定の改善対象であり、勝因の捏造理由にならない。無制限API消費を前提にしない。

\`seo_case_list\`: 発見時刻順ページング。 \`seo_case_get\`: 単件の根拠詳細。 \`seo_case_summary\`: 最大100件の1ページサンプルからテーマ分布と表層的な検索語の型を出す（勝因ではない）。たくさんの事例を横断分析する時はカーソルを進めて複数ページを集め、分析対象範囲を明記する。

Web UI は \`?view=cases\` の **SEO事例**。絞り込み、関連クエリ、確認済みの登録情報、上位記事へのリンクと短い本文断片を表示する。現時点の保存実数が0なら空画面を出し、架空の事例を埋めない。

## 調査の進め方

1. 既存の公開検索結果、候補KW、コミュニティで観測された具体的需要から、ジャンルを偏らせず複数の種を選ぶ。ひとつの売れ筋アフィリエイトテーマだけで増やさない。娯楽・仕事・学習・生活・実用的なDBなどを横断する。
2. 同じドメインの追跡ではなく、**初回発見の多様性**、異なるサイト構造、コンテンツ形態、情報の収集単位に注目しながら1件ずつ保存する。記事をページごとにDB複製しない。
3. 具体的な仮説（誰が何を探し、何の独自情報が価値を持つか）が浮かんだら、失敗事例・古いドメイン・元記事・一次資料などの反証と比較。単なる上位出現は成功認定しない。
4. 新サイトのテーマ案として見つけたらKeywords Idea Memoryに**別の正本のアイデア**として提出・評価し、このコーパスの元ドメイン・URL・検索語へ参照を張る。管理済サイトの施策化はSites Operatorの現行Planner/Worker正本を守る。

## 現状の限界

- 自動巡回スケジュール、AIによる記事の構造判定、Wayback、被リンク履歴、全SERPでの網羅調査、GSC内の実アクセス確認は未実装。新サイトの「ランキング勝者認定」は未実装であり、順位観測候補DB。
- 正しい公的サフィックスデータを全面実装したものではないため、特殊なドメインは手動照合が必要。
- 大量収集を効率化するには次段で**ジャンル別seed供給、既登録サイトのRDAP再照会抑制、検索語の多様性最適化**が有望。クォータとVercel実行時間を見ずに200語を1回に増やすことはしない。
- SEO Managerの定期ジョブ・Github Actionsトリガー・自動発行Taskは今回変更しない。

## 確認

\`npm run test:mcp\` → \`npm run typecheck\` → GitHub CI → Vercel Production SHA → Keywords \`remote_keyword_status\` (v1.22.0 / 47 tools)、UIの実データ状態をreadback。DB投入前にデータが大量に集まったと主張しない。
