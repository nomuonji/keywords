# ヘッドレス記事制作の改善仕様

2026-09-09。ユーザーの追加方針：UIは進捗確認用。ブラウザもAPIサーバーも起動しなくても、エージェントが最小の介入で成果物を作る。これは設計レビューと段階的な実装仕様であり、以下の全機能が実装済みという意味ではない。

## コアと責務

実行の正本は既存SQLとcommands。ヘッドレスworkerが対象選定・実行・再開を担い、CLI/MCP/UIは同じ状態を読む。UIを閉じても処理は継続する。UIからの開始操作や画面ポーリングを生成の前提にしない。API schedulerとrunnerの二重tickを廃止し、workerにスケジュール責任を集約する。手動tickも同じ排他制御を使う。

Blogは記事ファイルとサイト別buildの正本として残す。KeywordsのOperationは制作依頼、work_sessionは予算と再開位置、Blog itemはサイト側の実行単位。同じ仕事を別々に優先順位付けしない。handoff IDで対応づけ、新しいqueueや独自agent台帳を追加しない。

## 最短の制作経路

1. 接続・権限・予算を確認し、成果物に最も近い1件を選ぶ。途中の本文、未解決の検証失敗、根拠付き企画を、新しい候補探索より先に扱う。
2. 既存記事と必要な根拠だけ確認する。十分な材料があれば探索を省略する。不足する主張だけ外部調査し、記事に使わない候補を大量に保存しない。
3. 同じ制作依頼の中で本文を実ファイルへ保存する。企画だけで担当を終了し、次の全体tickを待つ構成を避ける。原典と対象読者、答える問い、既存記事との差分は維持する。
4. 保存済み本文を機械検証と内容レビューにかける。修正は失敗箇所だけに限定する。版が変わらなければ同じレビューを繰り返さない。
5. 本文の場所、差分、根拠、検証結果を記録し、ローカル成果物として完了する。公開設定が許可する場合だけ、その後に既存の公開経路へ進む。

この順序は固定の全段階必須pipelineではない。現在の成果物と欠けた条件から次のcommandを選ぶ。既に満たした段階は飛ばす。

サイトマップとGSCは別の保守作業。公開URLの証拠が必要な判断には取得を要求するが、ローカル下書きを作るだけの処理をDNS障害で塞がない。ローカル一覧は公開証拠とは表示しない。停止済みsessionから無断で別作業へ移るのではなく、依存関係の違う制作依頼として予算・許可を判定する。

## 無駄を減らす

| 現状の無駄 | 改善 |
|---|---|
| 17サイト等を一度にtickし未着手Operationを蓄積 | 空き実行枠に合わせて少数だけ着手。公平性と成果物までの残り作業で選ぶ |
| 小さな同期にも大きなAgentを起動 | 決定的な同期はcommandsで処理し、Agentは資料判断と執筆に使う |
| 起動ごとに全MCP・多数のskill・長い一般指示 | 制作に必要な接続と短いサイト別contextだけ渡す。秘密をpromptに載せない |
| 同じ原典と主張を複数schemaへ手入力 | 主張と原典を一度記録し、brief/交換packetをそこから生成 |
| 企画評価後に別Operationを新規作成して本文まで待つ | 同じ制作依頼に本文と再開位置を紐づけ、受け渡しを冪等化 |
| 成果が出る前に全サイトの指標を更新 | 当該記事の判断を変える指標だけ取得。全体保守は別予算 |
| 採点・不合格・同じ採点を反復 | 内容ハッシュと検証器版で結果を再利用し、修正版だけ検査 |
| 「確認のため」の大量ログと更新 | 状態変化と実行結果だけ永続化。heartbeatと成果の進展を区別 |

## 中断に対する設計

永続化する再開情報は、対象記事ID、完了した処理、成果物パスとハッシュ、使用source ID、失敗分類、次のcommand、残予算。私的な思考や会話全量を再開情報として保存しない。

| 中断箇所 | 再開時の処理 |
|---|---|
| 調査済み・本文未保存 | 保存済みsourceから執筆。期限切れ・欠落資料だけ再取得 |
| 本文保存後・DB更新前 | 同じ記事IDとハッシュでファイルを照合し、記録を補完 |
| DBに参照あり・ファイルなし | 成功にしない。保存処理の再実行または明確な欠損理由を記録 |
| 検証途中 | 本文と検証器の版を確認し、未完検証だけ実行 |
| Blog受領後・応答喪失 | 同じhandoff IDで照会/再送。新規記事を二重作成しない |
| worker停止・lease切れ | 旧所有権を失効させ、同じ仕事を再取得。古いworkerの書き込みは世代番号で拒否 |
| 利用上限・認証障害 | executor単位で待機し、サイトを連鎖blockedにしない。復旧条件成立後だけ再試行 |
| DNS/サイト固有障害 | 依存する処理だけ停止。無関係なサイトは続行 |
| 人間判断待ち・明示停止 | 判定対象の処理を進めない。解決後の共有状態を確認して再開 |

ファイル保存は同一ディレクトリ内の一時ファイルからrenameする等で部分書き込みを避ける。DBとファイルは一つのtransactionにはならないので、どちらが先に完了しても照合で復旧できるようにする。外部操作はexactly-onceを仮定せず、同一キーでの再実行を安全にする。

リトライは一か所で管理する。指数バックオフと上限、次回実行時刻を既存DBに永続化し、プロセス再起動で回数をリセットしない。実行中の上限はheartbeatだけで延命しない。最終成果更新時刻と実働時間で無進展を検出する。SIGTERM等では新規claimを止め、保存/記録を終えて所有権を解放する。強制終了はleaseと照合で回復する。

## 完了と品質

生成完了：本文ファイルが存在し、空でなく、対象サイト・記事ID・版が一致し、必須検証を通過。起動終了コード0、企画承認、handoff作成は生成完了ではない。

内容検証：主要主張を原典へ照合し、既存記事との重複、問いへの回答、出典、捏造された体験・数値を確認する。Agentの自己申告点数は補助情報に留める。レビューを別Agentにする場合も必要な記事・原典だけ渡す。機械検証は構文、リンク、サイト固有build等を担当。短い本文に形式項目を増やすだけのゲートは削る。

公開完了：別途許可された公開操作と実配信の確認。検索成果：後日の実測。この三者を混同しない。

## UIの縮小

UIは任意の観測窓。実行基盤の状態、現在の記事、直近の成果物、停止理由、次回再試行だけを表示する。常時開く必要はない。Operation・lease・run・細かなスコアは詳細へ。記事制作、承認、handoffをユーザーが画面で順番に押す必要をなくす。通常の介入は初期設定と停止、例外判断だけ。

## 受入検証

- UI/APIを停止しても、worker単独で1記事をローカル完成まで生成する。
- 調査後、本文保存直後、受領応答前、検証途中で強制終了しても、同じ記事から再開し重複を作らない。
- 利用上限が1回発生しても、後続サイトに失敗記録を連鎖させない。
- 権限なしの先頭候補と停止中sessionを除外して、実行可能な後続を取得する。
- 成果なしの終了コード0を完了扱いにしない。
- 資料が十分な企画からは探索を追加せず本文を作る。
- 秘密情報がprompt・ログ・runs・成果物に混入しない。

計測するのは最初の本文までの時間、ローカル完了までの時間/費用、再開時の重複作業量、人間介入回数、無進展リトライ回数。目標値は1記事の実測後に設定する。tick数・候補数・ONサイト数を成果に数えない。

## この更新で実施したことと残作業

実施：候補選択で有効な自動運転/委任を調べて後続へ進む修正、停止中子sessionの除外、隔離DBでの回帰検証、autopilot-smokeのDB削除リスク除去、従来監査のヘッドレス前提への追補。

未実施：worker単独スケジューラへの統合、共通障害の永続バックオフ、実働予算・無進展検知、生成成果物による完了判定、Blog実記事の縦通しと強制終了試験、UI縮小。これらを完了するまで「自律記事生成が完成」とは扱わない。
